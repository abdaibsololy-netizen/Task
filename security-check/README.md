# فحص أمني لموقع تملكه — أدوات جاهزة

هذا المجلد فيه سكربت فحص **غير تخريبي** يشتغل من جهازك على موقعك
(`http://20.215.186.30` أو أي هدف آخر تملكه وتصرّح باختباره)، ويولّد تقرير
Markdown بالعربي.

> **ليش ما فحصته أنا؟** بيئة التشغيل عندي تسمح بالخروج فقط إلى نطاقات محددة
> (GitHub وnpm وPyPI). جرّبت الاتصال بالعنوان: منفذ 80 يفتح ثم يُقطع الاتصال
> فورًا، والمنفذ 443 يفشل في مصافحة TLS. جرّبت عنوانًا محايدًا (`1.1.1.1`) وطلع
> نفس السلوك، بينما `github.com` يشتغل — يعني **المشكلة في وسيط الشبكة عندي،
> وليست بالضرورة في موقعك**. عشان كذا جهّزت لك أدوات تشتغل من جهازك.

---

## 1) تشغيل سريع

```bash
cd security-check
chmod +x audit.sh

# فحص أساسي
./audit.sh --target http://20.215.186.30 --out ./audit-out

# مع اختبار رصد WAF/IDS (حِزم شبيهة بالهجوم بلا استغلال)
./audit.sh --target http://20.215.186.30 --out ./audit-out --active
```

المخرجات:

- `audit-out/report.md` — التقرير الكامل (هذا اللي تقرأه).
- `audit-out/findings.tsv` — الملاحظات بصيغة `الخطورة<TAB>العنوان<TAB>الدليل`.
- `audit-out/.tmp/` — الردود الخام إن احتجت تدقيق.

**شغّله من خارج شبكة الموقع** (VPS، جهازك، أو حتى هوت سبوت الجوال). الفحص من
نفس السيرفر قد يمر على `localhost` ولا يشوف الـWAF ولا الـproxy.

## 2) وش يفحص بالضبط؟

| القسم | المحتوى |
|---|---|
| الاتصال والتحويل | الحالة، زمن الاستجابة، هل HTTP يعيد إلى HTTPS |
| الهيدرات الأمنية | HSTS، CSP، X-Frame-Options، X-Content-Type-Options، Referrer-Policy، Permissions-Policy |
| بصمة الخادم | `Server`، `X-Powered-By`، Cloudflare / Azure Front Door |
| الكوكيز | `Secure` و`HttpOnly` و`SameSite` على كل `Set-Cookie` |
| TLS | صلاحية الشهادة، الأسماء البديلة، هل TLS 1.0/1.1 مفعّل |
| مسارات حسّاسة | `.git/HEAD`، `.env`، نسخ احتياطية، `phpinfo`، `actuator`، `swagger`، `admin`، … |
| طرق HTTP | `OPTIONS`، و`TRACE` (Cross-Site Tracing) |
| الأخطاء | هل صفحة 404 تسرّب Stack Trace أو اسم قاعدة البيانات |
| حدود المعدل | 20 طلبًا على `/` وهل يظهر 429/403 |
| الرصد (اختياري) | SQLi/XSS/Traversal/SSTI/Command بلا استغلال — فقط لمعرفة هل يُرصد |

### وش **ما** يفحصه

- منطق التطبيق: IDOR، تصعيد صلاحيات، منطق الرصيد/الدفع، سباق العمليات.
- الحقن الحقيقي في نقاط النهاية الفعلية — يحتاج جلسة مصادق عليها وBurp/ZAP.
- الأسرار داخل كود الموقع أو داخل تاريخ Git.
- إعدادات السحابة (Azure NSG، مفاتيح التخزين، صلاحيات Managed Identity).
- ثغرات المكتبات (تحتاج `npm audit` / `pip-audit` / OWASP Dependency-Check على الكود نفسه).

## 3) كيف تقرأ الخطورة؟

| الخطورة | معناها | التصرف |
|---|---|---|
| `CRITICAL` | كشف مباشر لملف حسّاس (`.git` أو `.env`) | أغلق المسار الآن — ده يعني احتمال تسريب كود/مفاتيح |
| `HIGH` | تسريب معلومات، شهادة منتهية، TLS قديم، مسار إداري مكشوف | إصلاح عاجل |
| `MEDIUM` | هيدر ناقص مهم، كوكي بلا HttpOnly، TRACE مفعّل | إصلاح خلال أيام |
| `LOW` | تحسينات دفاعية (بصمة الخادم، Referrer-Policy) | ضمن التحسين المستمر |
| `INFO` | ملاحظة تحتاج مراجعة يدوية | — |

⚠️ **صفر ملاحظات لا يعني «آمن»**. الفحص السطحي يغطي الإعدادات الشائعة فقط.
الاختراق الحقيقي يحدث غالبًا في منطق التطبيق نفسه.

## 4) كيف تتأكد أن نظام كشف التهديدات **يرصد فعلًا**؟

هذا هو الجزء الأهم بالنسبة لك — نظامك ما ينفع إذا ما شاف الهجوم أو ما نبّهك.
شغّل `--active` وراقب لوحة نظامك في نفس الدقيقة. المتوقع:

| الاختبار | وش لازم يظهر في نظامك |
|---|---|
| مسح `/.git/HEAD` و`/.env` وغيرها | تنبيه «Sensitive Path Scan» + IP المصدر + قائمة المسارات + عدد 404 |
| `TRACE` / `OPTIONS` غير معتادة | تسجيل طريقة HTTP + تنبيه إن كانت خارج المسموح |
| `/?q=1' OR '1'='1` | تنبيه WAF/SQLi مع الـpayload الخام كما وصل |
| `/?q=<script>alert(1)</script>` | تنبيه XSS + هل الحجب مطبّق أم رصد فقط |
| `/?q=../../etc/passwd` | تنبيه Path Traversal |
| 20 طلبًا في 4 ثوانٍ | Rate-limit / سكان نشاط — أو على الأقل تجميع في تنبيه واحد |
| `User-Agent: OwnerAudit/1.0` | تسجيل الـUA (يساعدك تتأكد أن الطلبات وصلت أصلًا) |
| 404 متكرر من نفس الـIP | تنبيه Enumeration |

**مهم جدًا:** تأكد أن الطلب وصل للخادم أصلًا. افتح سجلات الـreverse proxy
(Nginx/Apache/Azure Front Door) وابحث عن المسار `/.git/HEAD` والـUA أعلاه.
إذا ما وصل → الحماية عندك على مستوى الشبكة (NSG/Firewall) وهي تشتغل، بس ما
تشوف الهجمات اللي تجاوزتها. وإذا وصل وما سجّل النظام → مشكلة تغطية.

### أسئلة تشخيصية

- هل التنبيه فيه **IP المصدر الحقيقي**؟ لو كله `127.0.0.1` أو IP الـproxy → إعدادات `X-Forwarded-For` غلط.
- هل فيه **توقيت** و**المسار الكامل** و**الـpayload**؟ تنبيه بلا تفاصيل ما ينفع للتحقيق.
- هل فيه **تصنيف خطورة** و**إجراء** (حجب/تسجيل)؟
- هل يشتغل **كشف+حجب** أو **كشف فقط**؟ إذا كشف فقط، الخطوة التالية ربطه بجدار الحماية.
- كم **إنذار كاذب** في اليوم؟ نظام يصيح على كل شيء = ما أحد يقرأه.

## 5) فحوصات يدوية مكمّلة

### أ) الدخول
جرّب 5–10 محاولات دخول خاطئة يدويًا على `/login` من متصفحك:
- هل يظهر قفل مؤقت أو تأخير؟
- هل الرسالة تفرّق بين «المستخدم غير موجود» و«كلمة المرور خطأ»؟ (تسريب معلومات)
- هل يوجد MFA؟

### ب) الجلسة
بعد تسجيل الدخول، DevTools ← Application ← Cookies:
- كوكي الجلسة `HttpOnly` + `Secure` + `SameSite`.
- سجّل خروج ثم أعد استخدام الكوكي القديم — هل انتهت صلاحيته فعلًا؟

### ج) صلاحيات الوصول (IDOR)
لو عندك موارد برقم مثل `/api/reports/123`، غيّر الرقم إلى `124` وأنت مسجّل
بمستخدم ثانٍ. إذا انفتح → ثغرة تصعيد وصول (منطق تطبيق، لا يكتشفها أي سكانر).

### د) وكيل اعتراض
ثبّت **Burp Suite Community** أو **OWASP ZAP**، مرّر عليه متصفحك، وسجّل
الدخول. هذا يعطيك نظرة على كل طلب بين المتصفح والخادم، وتقدر تعيد إرسالها
بتعديلات آمنة. **لا تستخدم Repeater لإرسال حقن مدمّر على بيانات حقيقية.**

### هـ) سجلاتك أنت
- هل تحتفظ بالسجلات 30–90 يوم؟
- هل فيها IP وUA والمسار والـbody (بحذر، قد يحتوي بيانات مستخدمين)؟
- هل فيه تنبيه عند **تسجيل دخول ناجح** من IP جديد؟

## 6) ملاحظات مهمة قبل ما تشغّل

- **التصريح:** شغّل هذا على أنظمة تملكها أو عندك تفويض كتابي باختبارها فقط.
- **التوقيت:** تجنّب أوقات الذروة، والفحص يستغرق أقل من دقيقة.
- **بيانات حقيقية:** إذا الموقع عليه مستخدمون، لا تختبر أي شيء يكتب/يعدّل/يحذف.
  السكربت هنا كل طلباته `GET`/`OPTIONS`/`TRACE` فقط.
- **بعد الإصلاح:** أعد التشغيل وقارن `findings.tsv` قبل وبعد — هذا يقيس تحسّنك.
